# 16 - Step-by-step: persistent Magisk root on the Moto E32

This is the working procedure for giving the XT2227-1 (`hawaii`, Unisoc T606,
Android 11, kernel 4.14.199) **persistent root** with Magisk, on top of the
software-unlocked bootloader from [07](07-unlock-how-to.md).

Result: `magiskd` runs on every boot, `adb shell su` works without any
exploit, Zygisk modules can be installed, and the bootloader stays unlocked
(`ro.boot.flash.locked=0`, `verifiedbootstate=orange`).

Proven 2026-10-31 with Magisk v31.1 on this device. The image that is
actually flashed is `D:\AndroidSDKTools\pi\boot_magisk_avb.img`
(sha256 `90416c09...cad3c`).

Two things make this device unusual:

* **fastboot cannot flash.** The bootloader's fastboot *download* gate
  rejects unsigned images ([11](11-flash-gate.md)), so the boot image is
  written with `dd` from a rooted shell. The runtime exploit
  ([03](03-root-exploit.md)) provides that one-time root.
* **The boot image must be re-signed.** Magisk keeps the OEM AVB footer,
  which then describes the *old* payload. TrustOS rejects it (`a0=6`) and
  U-Boot reboots, so the footer has to be rebuilt with a throwaway key.
  (An unlocked bootloader tolerates `a0=5` "public key rejected" but not
  `a0=6` "invalid metadata" - which is exactly why the signature has to be
  *valid*, not merely present.)

Safety net: `boot_a` holds the rescue/restore image from
[12](12-slot-b-testing-channel.md). Put it there **before** step 4 - a bad
`boot_b` then costs one power cycle, not the device.

## 0. Preconditions

| what | where | note |
|---|---|---|
| bootloader unlocked | see [07](07-unlock-how-to.md) | required: the AVB footer is signed with a throwaway key |
| runtime root exploit | `artifacts/mali_kroot` | one-time root, used to write `boot_b` |
| `boot_a` = rescue image | `artifacts/rescue/boot_rescue_restore.img` | **install first** - the safety net |
| stock `boot_b` backup | `D:\AndroidSDKTools\backups\hawaii-2026-10-30\backup\boot_b.img` | sha256 `ccd0faff...4f7b18` |
| Magisk v31.1 APK | `D:\AndroidSDKTools\pi\Magisk-v31.1.apk` | 10,679,283 B |
| Magisk patcher stage | `D:\AndroidSDKTools\pi\stage\` | extracted from the APK, see step 2 |
| avbtool | `D:\AndroidSDKTools\avb\avbtool.py` | footer rebuild |
| throwaway AVB key | `artifacts/kernel-build/avb-test-key.pem` | generated by `scripts/host/build_avb_boot.py` |
| prebuilt result | `D:\AndroidSDKTools\pi\boot_magisk_avb.img` | skip steps 2-3 if this file is present |

Host tools: `adb` (platform-tools), `sha256sum` (or `Get-FileHash`),
`python` for avbtool.

## 1. Check the device before touching anything

**Before Magisk is installed the exploit is the only root available**, and it
elevates just the shell it runs in - so each root command below needs its own
`mali_kroot` run. (That is also why the exploit is not used any more once
step 5 is done.)

```bash
adb devices
adb shell getprop ro.boot.slot_suffix      # must be _b
adb shell 'chmod 755 /data/local/tmp/mali_kroot; /data/local/tmp/mali_kroot >/dev/null 2>&1;
  sha256sum /dev/block/by-name/boot_b'
```

Expected: `_b` and
`ccd0faff51ab24d921b2671c562f0fe08e7a1ba2b7f19bb93a5f2650eb4f7b18`
(the stock image). **Abort if the hash differs** - something else was
flashed and the reasoning below no longer applies.

Also check that the safety net really is in place:

```bash
adb shell 'chmod 755 /data/local/tmp/mali_kroot; /data/local/tmp/mali_kroot >/dev/null 2>&1;
  sha256sum /dev/block/by-name/boot_a'
# compare with artifacts/rescue/boot_rescue_restore.img
```

And look at the A/B metadata (slot b should still have tries remaining):

```bash
adb shell 'chmod 755 /data/local/tmp/mali_kroot; /data/local/tmp/mali_kroot >/dev/null 2>&1;
  dd if=/dev/block/by-name/misc bs=1 skip=2048 count=32 2>/dev/null | od -An -tx1'
# decode with scripts/host/misc_ab.py
```

## 2. Stage Magisk's patcher on the device

Magisk's own patcher lives inside the APK. Either use the pre-extracted
stage in `D:\AndroidSDKTools\pi\stage\`, or extract it from the APK
(rename to `.zip`, unzip; the binaries are the `libmagisk*.so` /
`libbusybox.so` files in `lib/arm64-v8a/`, the scripts are in `assets/`):

| APK entry | becomes |
|---|---|
| `lib/arm64-v8a/libmagiskboot.so` | `magiskboot` |
| `lib/arm64-v8a/libmagiskinit.so` | `magiskinit` |
| `lib/arm64-v8a/libmagisk.so` | `magisk` |
| `lib/arm64-v8a/libbusybox.so` | `busybox` |
| `assets/init-ld` | `init-ld` |
| `assets/boot_patch.sh` | `boot_patch.sh` |
| `assets/util_functions.sh` | `util_functions.sh` |
| - | `dos2unix` shim: `#!/system/bin/sh` + `exec cat` |

```bash
adb push D:\AndroidSDKTools\pi\stage /data/local/tmp/pi/stage
adb push D:\AndroidSDKTools\backups\hawaii-2026-10-30\backup\boot_b.img /data/local/tmp/pi/stock_boot_b.img
adb shell chmod 755 /data/local/tmp/pi/stage/*
```

## 3. Patch the stock boot and re-sign it

Do the patch **on the device** - Magisk's `boot_patch.sh` needs Android's
`magiskboot`. Run it in a shell that the exploit has elevated (Magisk is not
installed yet, so there is no `su`):

```bash
adb shell 'chmod 755 /data/local/tmp/mali_kroot; /data/local/tmp/mali_kroot >/dev/null 2>&1;
  cd /data/local/tmp/pi/stage && BOOTMODE=true sh boot_patch.sh ../stock_boot_b.img'
```

It produces `new-boot.img` next to the input. Pull it and inspect:

```bash
adb pull /data/local/tmp/pi/stage/new-boot.img D:\AndroidSDKTools\pi\magisk_patched_raw.img
python D:\AndroidSDKTools\avb\avbtool.py info_image --image D:\AndroidSDKTools\pi\magisk_patched_raw.img
```

What you see:

* `Original image size: 34932736` (the stock was `34721792` - Magisk's
  ramdisk is bigger),
* but the **hash descriptor still says `Image Size: 34721792`** and the
  public key is still the OEM one (`a46323df...`). That footer describes
  the *old* payload: flashing it as-is gives a bootloop.

So rebuild the footer: payload = the first `Original image size` bytes of
the patched image, signed with the throwaway key.

```bash
# 1) payload = first 34932736 bytes (drop the stale footer)
python -c "d=open(r'D:\AndroidSDKTools\pi\magisk_patched_raw.img','rb').read(); open(r'D:\AndroidSDKTools\pi\boot_magisk_payload.bin','wb').write(d[:34932736])"

# 2) AVB hash footer, same salt and rollback index as the stock image.
#    avbtool pads the result to --partition_size (64 MiB).
python D:\AndroidSDKTools\avb\avbtool.py add_hash_footer \
  --image D:\AndroidSDKTools\pi\boot_magisk_payload.bin \
  --partition_name boot --partition_size 67108864 \
  --key artifacts/kernel-build/avb-test-key.pem \
  --algorithm SHA256_RSA4096 --rollback_index 2 \
  --salt f83b993601311bca149a573c1e737666ff011f6cf2aa2a5ae822f91b97af0991

# 3) rename into place and hash it
mv D:\AndroidSDKTools\pi\boot_magisk_payload.bin D:\AndroidSDKTools\pi\boot_magisk_avb.img
sha256sum D:\AndroidSDKTools\pi\boot_magisk_avb.img
# expected: 90416c09f6359fdcc0711f36e214454421c42598518787f58c1916be6c5cad3c
```

Verify the new footer describes the new payload:

```bash
python D:\AndroidSDKTools\avb\avbtool.py info_image --image D:\AndroidSDKTools\pi\boot_magisk_avb.img
```

`Original image size` and the hash descriptor's `Image Size` must both be
`34932736`, and the public key must now be the throwaway one
(`dcc2433b...`), not the OEM key.

## 4. Write it to boot_b

The exploit elevates only the shell it runs in, so the whole write has to
happen in **one** `adb shell` invocation. (Magisk is not installed yet, so
`su` does not exist - root comes from `mali_kroot`.)

```bash
adb push D:\AndroidSDKTools\pi\boot_magisk_avb.img /data/local/tmp/pi/boot_magisk_avb.img
adb shell sha256sum /data/local/tmp/pi/boot_magisk_avb.img
# expect 90416c09f6359fdcc0711f36e214454421c42598518787f58c1916be6c5cad3c
```

Write it:

```bash
adb shell 'chmod 755 /data/local/tmp/mali_kroot
/data/local/tmp/mali_kroot >/dev/null 2>&1
set -e
echo "uid=$(id -u)"
# 1) refuse to touch a non-stock boot_b
dd if=/dev/block/by-name/boot_b bs=1M count=64 2>/dev/null | sha256sum
# must print ccd0faff51ab24d921b2671c562f0fe08e7a1ba2b7f19bb93a5f2650eb4f7b18
# 2) write the new image
dd if=/data/local/tmp/pi/boot_magisk_avb.img of=/dev/block/by-name/boot_b bs=1M
sync
# 3) read back and compare
dd if=/dev/block/by-name/boot_b bs=1M count=64 2>/dev/null | sha256sum
# must print 90416c09f6359fdcc0711f36e214454421c42598518787f58c1916be6c5cad3c
'
```

Then set slot b to **one** boot attempt, so a hang falls back to the `boot_a`
rescue on its own:

```bash
adb push scripts\device\set_slot_b_tries1.sh /data/local/tmp/set_slot_b_tries1.sh
adb shell 'chmod 755 /data/local/tmp/mali_kroot /data/local/tmp/set_slot_b_tries1.sh; /data/local/tmp/set_slot_b_tries1.sh'
```

The A/B block becomes: slot a = priority 14, tries 0, successful 1 (`0x008e`);
slot b = priority 15, tries 1, successful 0 (`0x001f`); crc32 `0x20a582b1`.
`set_slot_b_tries1.sh` runs the exploit itself, so it needs its own root
shell.

## 5. Reboot and verify

```bash
adb reboot
# ~50 s later
adb devices
adb shell getprop sys.boot_completed        # 1
adb shell getprop ro.boot.slot_suffix        # _b
adb shell getprop ro.boot.verifiedbootstate  # orange (the unlock state is unchanged)
adb shell ps -A | grep magisk                # root ... magiskd
```

Then install the manager app and let it hand `su` to the shell user:

```bash
adb install D:\AndroidSDKTools\pi\Magisk-v31.1.apk
```

In the app: allow **su** for the shell/adb user (open the app once - the
manager has to create its database before the policy row below can be
written). From the host the same thing is one row in Magisk's database
(`policy 2` = allow):

```bash
adb shell "su -c '/debug_ramdisk/magisk --sqlite \"INSERT OR REPLACE INTO policies (uid,policy,until,logging,notification) VALUES (2000,2,0,1,1)\"'"
```

From then on:

```bash
adb shell "su -c 'id'"    # uid=0(root) gid=0(root) ... context=u:r:magisk:s0
```

**Note:** the exploit run in step 4 left SELinux Permissive for that boot.
The reboot cleared it - check `adb shell getenforce` -> `Enforcing`. A
Permissive kernel is a tamper signal and costs the Play Integrity BASIC
verdict ([15](15-play-integrity.md)).

## 6. Modules (optional)

Everything from here is in [15-play-integrity.md](15-play-integrity.md):

- **Zygisk**: Magisk's built-in (Settings > Zygisk) or Zygisk Next. If Zygisk
  Next is used, Magisk's built-in Zygisk must be **off** and a module needs a
  `mazoku` marker next to its `machikado` file, otherwise ZN silently ignores
  it (that is why Shamiko 1.2.5 does not load under ZN - check
  `/data/adb/zygisksu/modules_info` for what was actually loaded).
- **PlayIntegrityFix-NEXT v3.0** (props + attestation), **TrickyStore 1.4.1**
  (keybox), **Shamiko** (root hiding).

Install a module from a zip on the device (Magisk's CLI lives in the
ramdisk, hence the full path):

```bash
adb push module.zip /data/local/tmp/module.zip
adb shell "su -c '/debug_ramdisk/magisk --install-module /data/local/tmp/module.zip'"
```

and reboot.

## 7. Rollback

Restore the stock boot image (from a rooted shell):

```bash
adb shell "su -c 'dd if=/data/local/tmp/pi/stock_boot_b.img of=/dev/block/by-name/boot_b bs=1M; sync'"
```

or through fastboot/BootROM if the download gate ever opens
([13](13-recovery-bootrom.md), [14](14-brom-recovery-runbook.md)). Note that
the `boot_a` rescue also restores a **stock** `boot_b` - if it fires, Magisk
is gone and this procedure has to be repeated.

## 8. Pitfalls

| symptom | cause / fix |
|---|---|
| bootloop right after the write | the stale OEM AVB footer was flashed (step 3 not done). The `boot_a` rescue fixes it: power-cycle once, the SPL falls back to slot a and restores stock `boot_b` |
| TrustOS `a0=6`, U-Boot reboots | same as above - invalid vbmeta metadata |
| `magiskd` not running | the image was not really written (check the read-back hash) or the slot suffix does not match the image |
| `su` missing after install | the Magisk app has not granted the shell user yet, or `magiskd` is not running |
| the exploit dies with SIGBUS | known flakiness ([04](04-reliability-hardening.md)) - just retry |
| `getenforce` shows `Permissive` | the exploit ran in this boot; reboot to get `Enforcing` |
| `adb shell su` says "not allowed" | grant the policy row (step 5) |
| fastboot refuses to flash | expected - the download gate ([11](11-flash-gate.md)); use `dd` |
| modules do not load | check the Zygisk provider and the `machikado`/`mazoku` markers; `modules_info` lists what ZN loaded |

## 9. Checklist

- [ ] `boot_a` = rescue image in place **before** writing `boot_b`
- [ ] `boot_b` read-back sha256 == `ccd0faff...4f7b18` (stock) before the write
- [ ] image read-back sha256 == `90416c09...cad3c` after the write
- [ ] A/B block: slot b = one attempt (`0x001f`)
- [ ] after reboot: `magiskd` running, slot `_b`, `verifiedbootstate=orange`
- [ ] `adb shell "su -c 'id'"` -> `u:r:magisk:s0`
- [ ] `getenforce` -> `Enforcing` (not Permissive)
