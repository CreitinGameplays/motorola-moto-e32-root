## Root cause

The Unisoc boot-image `dtb` slot is not a bare FDT: it is a 64-byte
**Android DT_TABLE** (magic `0xd7b7ab1e`) followed by the FDT.  U-Boot parses
the table, iterates its entry/entries and picks the DTB that matches the
board before handing off to the kernel.  Two things broke that for our DTB:

1. **Missing root identity keys.**  The working vendor DTBs carry

   ```
   cpuinfo_hardware = "Unisoc ums9230";
   sprd,sc-id = "ums9230 1000 1000";       (vendor_t41)
   sprd,sc-id = "ums9230 4h10 DC4CPU";     (live 4h10 DTB)
   ```

   Our self-contained DTB had **neither**, so the matcher found nothing.
   Evidence: the device U-Boot binary (`artifacts/bootloader/bl/uboot_b.img`)
   contains, adjacent to the exact log string:

   ```
   0xc1703  Property sprd,sc-id is not formatted correctly
   0xc1a88  No matching DTB could be found
   ```

   plus the symbol `look_for_matching_device_from_dt`.  The public Unisoc
   source (`sprd-linux/u-boot15`, `common/loader/loader_nvm.c`) has the
   corresponding `load_fixup_dt_img()` / DT_TABLE reader.

2. **Wrong DT_TABLE field patched by the packer.**  The stock table is
   (all big-endian 32-bit words):

   ```
   header: [0] magic 0xd7b7ab1e [1] total_size [2] 0x20 [3] 0x20
           [4] entry_count=1 [5] 0x20 [6] 0x800 [7] version=0
   entry:  [8] dt_size       [9] dt_offset=0x40
   ```

   `wrap_sprd_dtb()` was writing the new DTB length into word **[7]**
   (byte 28, the version field), leaving the entry's `dt_size` at the stock
   **175402**.  Our DTB is only 60 KiB, so U-Boot read it as 175 KiB.
   The dtbo partition's table confirms the layout (`+0x20 = 0xc9d9` =
   first overlay size, `+0x24 = 0x60` = its offset), which is exactly what
   U-Boot printed as `merge_dtbo : offset = 0x20 size=0xc9d9`.

## ROOT CAUSE FOUND (2026-11-27 17:35) — stock init aborts on purpose

The live-serial hybrid boot finally captured **stock init's own messages**.
The death is not a silent kernel hang: init hits a fatal first-stage error
and SIGABRTs PID 1.

```
init: mount("sysfs", "/sys", "sysfs", 0, NULL) failed Device or resource busy
init: mount("selinuxfs", "/sys/fs/selinux", "selinuxfs", 0, NULL) failed No such file or directory
init: Init encountered errors starting first stage, aborting
init: InitFatalReboot: signal 6
  #04 android::init::FirstStageMain(int, char**)+5648
```

Two independent mistakes in the hybrid ramdisk:

1. **sysfs was pre-mounted on `/sys` by our own init.**  Stock first-stage
   init mounts sysfs on `/sys` and treats `EBUSY` there as **FATAL**, so it
   aborted before touching `/system`.  This is why every hybrid boot died
   ~0.3 s after the handover with no kernel message: `InitFatalReboot` →
   SIGABRT on PID 1 → kernel panic → the custom PMIC reset → lost RTC →
   cold 1970 slot-a rescue boot.  It also explains the empty
   `dmesg-ramoops` slot (the rescue's own `reboot()` overwrote the single
   record before it could be read).
2. **`CONFIG_LSM` did not contain `selinux`.**  The 7.1 tree's
   `security/lsm_init.c` *disables every LSM not listed in
   `CONFIG_LSM`*; the build had
   `CONFIG_LSM="landlock,lockdown,yama,loadpin,safesetid,ipe,bpf"`, so
   `selinux_init` never ran, `selinuxfs` was never registered,
   `/sys/fs/selinux` did not exist, and stock init's selinuxfs mount
   failed `ENOENT`.  `CONFIG_SECURITY_SELINUX=y` alone is not enough on
   this tree.

Fixes (no kernel rebuild needed):

* `scripts/host/logsave.c`: `SYSFS_ROOT` is `/sys2` for hybrid builds.
  `mount_pseudo()` mounts sysfs there (still `/sys` for the parked diag
  build), `gadget_setup()` builds configfs under `SYSFS_ROOT`, and the UDC
  bind is retried for 5 s.  `/sys` is left an empty directory for the
  stock init; `/proc` and devtmpfs are still mounted.
* Pack the 7.1 image with `--cmdline-extra "security=selinux"`:
  `security/lsm_init.c` then appends SELinux to the built-in order even
  though it is not in `CONFIG_LSM` (the SELinux LSM is
  `LSM_FLAG_LEGACY_MAJOR`, so `security=` selects it).  Use
  **`security=`**, not `lsm=`: `lsm=` overrides and clears `security=`.
* `H71_LIVE` adds a `/dev/kmsg → /dev/ttyGS0` relay (both fds opened
  *before* the handover, so the stock init's `/dev` remount cannot hide
  them) plus a busybox shell on COM6.

New image: `artifacts/testimages/boot_71_live2.img`, SHA256
`b5d035be6b9e5165b191d739f0e9a058f9697c38cfc3736427427d187c2cfa02`,
cmdline `console=ttyS1,115200n8 buildvariant=user security=selinux`.
Ramfs `71_hybridramfs_live2.cpio.gz` (482 entries, 23,159,600 B raw):

The generic `sprd_wdt` node arms the FIQ WDT at probe (`timeout-sec=12`);
stock uses `sprd,wdt-r2p0-fiq` and never arms it.  Disabling it is kept.

**Live eMMC log**: `H71_LIVE` forks a child that copies `/dev/kmsg`
records to `sysdumpdb +0x300000` (4 MiB) with `fdatasync` per record,
plus a 1 Hz `H71-PID1 (t=Ns)` snapshot (PID 1 syscall/wchan/stack/stat).
It survives a hard power-off.  **Caveat found later**: the window is
**not cleared** between boots; a shorter new boot leaves stale fragments
of the previous boot interleaved with the new records.  Parse only the
byte range written by the newest boot, and prefer the COM6 kmsg relay
capture (`com6_wait.ps1`) when both are available.

## live9: ROOT CAUSE — our `/sys2` mount breaks `SwitchRoot`

COM6 capture (`com6_live_capture.txt`, PORT OPEN 08:36:40.966):

appeared once `/system` was mounted.

all dm-linear partitions are created, `/system` mounts.

### live21 result: no USB at all

The eMMC log gave the exact cause:

```
UDC core: h71: couldn't find an available UDC or it's busy
udc musb-hdrc.10.auto: failed to start h71: -19
H71-INIT: UDC musb-hdrc.10.auto bind failed (16)
```

`ffs.adb.0` was never mounted: configfs splits function names at the
first `.`, so its FunctionFS instance name is **`adb.0`**, while adbd
mounts FunctionFS source **`adb`** (stock's own `g1/functions/ffs.adb`).
The composite bind failed with `-ENODEV` because the ffs function had
no descriptors, so not even the ACM interface enumerated.  Two further
facts from the stock device:

* the vendor `on init` (`init.ums9230_4h10.usb.rc`) **does** create
  `g1/ffs.adb` and mount `functionfs adb /dev/usb-ffs/adb` on 7.1 —
  which is why that mount succeeded in the live21 log;
* the ADB bind trigger requires
  `persist.vendor.sys.modem.diag=disable`, a persist property stored
  **only in `/data/property`** (never mounted on 7.1), and writes
  `/config/usb_gadget/g1/UDC ${sys.usb.controller}`, whose value is
  normally set by the USB HAL (which does not run here).

So stock init's own ADB path can never fire on 7.1.

### What live work established (live17 + /cache/h71 scripts)

* Stock's vendor `on init` creates `g1`, `functions/ffs.adb` and mounts
  FunctionFS `adb` at `/dev/usb-ffs/adb` on 7.1 — confirmed live.
* `sys.usb.controller` is already `musb-hdrc.10.auto` on the 7.1 boot.
* `apexd` only mounts the 6 bootstrap APEXes; `com.google.android.adbd.apex`
  is **not** activated.  It can be mounted manually:
  `unzip -o -d /cache/h71 /system/apex/com.google.android.adbd.apex apex_payload.img`,
  `losetup -r /dev/block/loop26 /cache/h71/apex_payload.img`,
  `mount -t ext4 -o ro /dev/block/loop26 /apex/com.android.adbd`.
* adbd runs from `/apex/com.android.adbd/bin/adbd` with
  `LD_LIBRARY_PATH=/apex/com.android.adbd/lib64`, opens `/dev/usb-ffs/adb/ep0`,
  writes descriptors (`ep1`/`ep2` appear) and, once g1 is bound with
  `functions/ffs.adb` linked into `configs/b.1/f1`, receives
  `FUNCTIONFS_BIND` and `FUNCTIONFS_ENABLE`.  So the USB ADB function
  itself works.

  unexpected length while reading header`; the kernel logs a harmless
  `musb-hdrc: request ... not queued to ep1in` (dequeue race).  Host

* `setprop` (even from the COM6 root shell, context `u:r:kernel:s0`)
  always fails: "Failed to set property ... See dmesg for error reason";
  raw `PROP_MSG_SETPROP` gets `n=0` (socket closed without reply).  The
  stock ADB trigger therefore cannot be armed.
* Host key seeded at `/data/misc/adb/adb_keys` on a tmpfs at `/data`
  (the real `/data` never mounts).  `ro.adb.secure=1`, no UI to tap Allow.

## SOLVED: host ADB on the 7.1 kernel (live17 + /cache/h71/tcp_rndis.sh)

The working combination (all run from the COM6 root shell after ~8 s):

1. `mount -t tmpfs tmpfs /data`, write the host `adbkey.pub` to
   `/data/misc/adb/adb_keys` (0644) — `ro.adb.secure=1`, no UI to tap Allow.
2. `setprop service.adb.tcp.port 5555` — **regular properties do work**
   from the COM6 root shell; only `ctl.*` control properties fail.
3. Mount the adbd APEX manually (apexd only activates bootstrap APEXes):
   `unzip -o -d /cache/h71 /system/apex/com.google.android.adbd.apex
   apex_payload.img`, `losetup -r /dev/block/loop26 /cache/h71/apex_payload.img`,
   `mount -t ext4 -o ro /dev/block/loop26 /apex/com.android.adbd`.
4. Start adbd directly with
   `LD_LIBRARY_PATH=/apex/com.android.adbd/lib64 /apex/com.android.adbd/bin/adbd`
   — it logs `adbd listening on tcp:5555`.
5. Rebuild the gadget **while unbound**: h71 VID/PID `04B3:4010`, config
   `c.1` with **only** `rndis.0` (remove `acm0`), then write the UDC.
   Those IDs are in Windows' inbox `netimm.inf`, so Windows binds the
   "IBM USB Remote NDIS Network Device" driver automatically.  With ACM
   still linked, Windows bound that driver to the composite *parent*
   (code 10) — RNDIS-only avoids it.
6. From the phone: `ip link set usb0 up`, `ip addr add
   192.168.42.1/24 dev usb0`.
7. Windows needs **no admin**: it takes an APIPA address on the RNDIS
   adapter, and both ends have IPv6 link-local.  Connect with
   `adb connect "[fe80::ff:fe00:1%52]:5555"` (%52 = Windows interface
   index of the RNDIS adapter, from `Get-NetAdapter`).

Verified: `adb -s "[fe80::ff:fe00:1%52]:5555" shell` returns
`Linux version 7.1.0-rc1-sprd+`, `uid=2000`, `ro.boot.slot_suffix=_b`.
`sys.boot_completed` is still empty — full Android boot remains blocked,
but a usable host shell on the 7.1 userspace is now available.
