2. STALE vs FRESH BOOTROM  (the core discovery)
------------------------------------------------------------------------
A BootROM node that has been sitting on the bus for a while ENUMERATES but
its command handler is dead. spd_dump attaches at the USB level and gets
nothing back:

  $ spd_dump --wait 8 verbose 2 sendcmdv 0x07 0 sendcmdv 0x0D 0
  libusb_control_transfer ok
  usb_recv failed : LIBUSB_ERROR_TIMEOUT      (x10)
  wrong command or wrong mode detected, reboot your phone by pressing
  POWER and VOL_UP for 7-10 seconds.

A FRESHLY entered BootROM (Power + Vol Down, then plug in) answers
immediately and identifies itself:

  libusb_control_transfer ok
  CHECK_BAUD bootrom
  BSL_REP_VER: "SPRD3\0"
  CMD_CONNECT bootrom

So the chip is alive and the link is good. The earlier "wrong command or
wrong mode" failures were a stale session left by the forced power-off,
not a dead or wrong chip.

Consequence: every probe must be armed BEFORE the device appears, and must
fire the instant a NEW enumeration shows up. Firmware idle window is only
a couple of minutes.

3. TOOL COMMAND PARSING: `sendcmdv` IS RUNTIME ONLY
------------------------------------------------------------------------
The 17:06 session above answered CHECK_BAUD + CONNECT and then timed out on
`chip_uid`. In addition, `sendcmdv` is a runtime command, not an initial
CLI command. Putting `sendcmdv ...` after `--wait` made spd_dump print its
usage and enter interactive `BROM >`; it did not run any query. Therefore
the earlier 0x07/0x2D attempt did not read anything. `spd_cmd.h` lists:

  0x1A BSL_CMD_READ_CHIP_UID   -> 0xAB BSL_REP_READ_CHIP_UID
  0x07 BSL_CMD_READ_CHIP_TYPE  -> 0x94 BSL_REP_READ_CHIP_TYPE
  0x0D BSL_CMD_READ_FLASH_INFO -> 0x9B BSL_REP_READ_FLASH_INFO
  0x2D BSL_CMD_READ_PARTITION  -> 0xBA BSL_REP_READ_PARTITION
  0x35 BSL_CMD_DUMP_UBOOT_LOG  -> 0xBB BSL_REP_DUMP_UBOOT_LOG
  0x19 BSL_CMD_CHECK_ROOT      -> 0xA7 if ROOT_MAGIC matches, else 0x80

These opcodes describe the protocol but this spd_dump CLI does not expose
them as normal commands. The matched UMS9230-UFS path is to load the

`r splloader`. The device-specific report confirms FDL1-DL hash
153F3A...C259C15; its FDL2-DL has hash 499F75...2F6BF and needs the call
at offset 0x7234 NOPed to access the partition table. It also reports the
five NOPs at 0x812bc. This is untested on our XT2227-1.

------------------------------------------------------------------------
4. WHY "NO LOGO, EVER" IS THE KEY FACT
------------------------------------------------------------------------
On this device the Motorola logo is drawn by the bootloader (U-Boot), from
the `logo` partition. The one KVM-off kernel test that reached userspace
showed: logo -> no adb -> hang (244 s). So U-Boot running == logo visible.

Observed since the hang: pure black, no logo, no backlight, not even a
flicker, on every power-on attempt, including a 3-minute untouched
Power-alone test. Therefore U-Boot never starts.

That moves the fault BELOW U-Boot:

    BootROM --(load + verify SPL from UFS)--> SPL/sml --> U-Boot --> boot.img

and it rules out everything we touched:
  * boot_b (the hung kernel) cannot matter - it is loaded by U-Boot, which
    never runs.
  * the misc A/B block cannot matter for the same reason.
  * the boot_a rescue cannot run for the same reason (it is boot.img too).

If U-Boot were running, the slot-b-exhausted fallback would pick slot a =
the proven restore rescue, which returns to Android in ~40-60 s of black.
Three untouched minutes produced nothing, so that path is not executing.

Also ruled out: a stuck Volume Down key. A stuck Vol-Down would make a
plain Power-on enter download mode (and enumerate). Plain Power does not
enumerate at all, so the strap is not stuck.

7. BOOTLOADER IMAGES ARE NOT FDL1/FDL2
------------------------------------------------------------------------
  sml_a.img     4448544201000000 ...  ("DHTB" wrapper)
  uboot_a.img   4448544201000000 ...
  trustos_a.img 4448544201000000 ...
`sml_a` is ARM Trusted Firmware / secure monitor (strings: SPRD System
Reset, teecfg, sprd_sip_svc, plat_sprd_psci_pm_ops). All three are
DHTB-wrapped and therefore are not keys to a BootROM download: they are
loaded BY the download.

No FDL1/FDL2 is published for ums9230 - the CVE repo carries only
custom_exec_no_verify_65015f08.bin (96 B) and stack-info-ums9230.csv.
On UFS a wrong FDL bricks (TomKing062), so that path needs the exact
vendor FDL from this device's own firmware package, not a guess.

------------------------------------------------------------------------
8. WHAT THIS MEANS
------------------------------------------------------------------------
The BootROM is healthy. The failure is that it is not getting from SPL to
U-Boot. Two candidate causes remain, and the read-only probe separates
them:

  (a) BootROM cannot initialise/read the UFS  -> 0x0D / 0x43 / 0x2D fail
      or return errors. Points at power/PMIC or UFS hardware.
  (b) UFS reads fine but the SPL is corrupt or fails verification
      -> 0x0D / 0x2D succeed. Needs an FDL-based reflash of uboot/sml.

Nothing in either case is fixable by touching boot_a/boot_b or misc.
