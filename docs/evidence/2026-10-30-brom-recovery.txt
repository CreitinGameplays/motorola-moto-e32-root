4. WHY "NO LOGO, EVER" IS THE KEY FACT
------------------------------------------------------------------------
On this device the Motorola logo is drawn by the bootloader (U-Boot), from
the `logo` partition. The one KVM-off kernel test that reached userspace
showed: logo -> no adb -> hang (244 s). So U-Boot running == logo visible.

Observed since the hang: pure black, no logo, no backlight, not even a
flicker, on every power-on attempt, including a 3-minute untouched
Power-alone test. Therefore U-Boot never starts.

That moves the fault BELOW U-Boot:

    BootROM --(load + verify SPL from UFS)--> SPL/sml --> U-Boot --> boot.img

and it rules out everything we touched:
  * boot_b (the hung kernel) cannot matter - it is loaded by U-Boot, which
    never runs.
  * the misc A/B block cannot matter for the same reason.
  * the boot_a rescue cannot run for the same reason (it is boot.img too).

If U-Boot were running, the slot-b-exhausted fallback would pick slot a =
the proven restore rescue, which returns to Android in ~40-60 s of black.
Three untouched minutes produced nothing, so that path is not executing.

Also ruled out: a stuck Volume Down key. A stuck Vol-Down would make a
plain Power-on enter download mode (and enumerate). Plain Power does not
enumerate at all, so the strap is not stuck.

8. WHAT THIS MEANS
------------------------------------------------------------------------
The BootROM is healthy. The failure is that it is not getting from SPL to
U-Boot. Two candidate causes remain, and the read-only probe separates
them:

  (a) BootROM cannot initialise/read the UFS  -> 0x0D / 0x43 / 0x2D fail
      or return errors. Points at power/PMIC or UFS hardware.
  (b) UFS reads fine but the SPL is corrupt or fails verification
      -> 0x0D / 0x2D succeed. Needs an FDL-based reflash of uboot/sml.

Nothing in either case is fixable by touching boot_a/boot_b or misc.

16. WHY SLOT SUFFIX IS THE PRIME SUSPECT
------------------------------------------------------------------------
misc is the ONLY partition that differs from the pre-failure backups.
Live block: slot_suffix "_b", a=0x008e (bootable), b=0x000f (unbootable).
If this U-Boot resolves the target slot from slot_suffix instead of the
BCAB priority/tries logic, it keeps booting slot b - the slot holding the
hung custom kernel - and never falls back to slot a. That matches
"backlight on, then failure" with no recovery.

Planned action: force slot_suffix "_a" using spd_dump set_active, whose
implementation (common.c:2537) writes, at misc+0x800:
    slot_suffix "_{slot}", magic BCAB, version 1, nb_slot 2,
    chosen slot prio 15 tries 6 succ 0, other slot prio 14 tries 1 succ 0,
    crc32_le over the first 28 bytes
Caveat: set_active is a read-modify-write of the whole 1 MB misc partition
(dump -> patch 0x800 -> write back), not a 32-byte poke.
Rollback: readback_write\misc_before_setslot.bin is a byte-exact copy, and
`wof misc 0x800 <file>` can restore.

19. WHO PICKS THE SLOT: THE SPL, NOT U-BOOT
------------------------------------------------------------------------
Searching the stock SPL payload (u-boot-spl-16k-ufs-sign.bin, 65480 B, the
same bytes present in flash) for printable strings finds the A/B boot set
and the misc partition name:

  0x0e1e0 sml_a        0x0e1f0 sml_b
  0x0e200 teecfg_a     0x0e210 teecfg_b
  0x0e220 trustos_a    0x0e230 trustos_b
  0x0e240 uboot_a      0x0e250 uboot_b
  0x0e2d6 misc

No "BCAB"/"slot_suffix"/"tries_remaining" ASCII strings exist (the struct
field names are compiler-only), but the partition set proves the SPL is
the component that resolves the A/B slot and loads uboot_X / sml_X /
trustos_X / teecfg_X before jumping to U-Boot.

Consequence: a slot-resolution failure occurs BEFORE U-Boot starts, so it
explains a boot that dies with no uboot_log entry, no logo and no
backlight. The earlier idea that U-Boot itself refuses slot b is
superseded but has the same fix.

Coherent timeline:
  * b bootable (prio15 tries1 succ1) -> SPL loads uboot_b -> U-Boot runs
    -> custom kernel hangs after backlight on (two logged sessions).
  * failed attempt burns b's retry and clears successful_boot
    -> b is prio15 but not bootable, suffix is still "_b"
    -> SPL has no usable U-Boot -> falls to download/BROM loop.
  * result: BROM cycles, no U-Boot, no logo, all flash images intact.

21. WRITE MECHANICS OF set_active (verified in source before writing)
------------------------------------------------------------------------
common.c:2537 set_active() builds a 32-byte block in RAM:
    slot_suffix "_{arg}", magic BCAB, version 1, nb_slot 2,
    chosen slot prio 15 tries 6 succ 0,
    other  slot prio 14 tries 1 succ 0,
    crc32 over the first 0x1C bytes.
then common.c:2451 w_mem_to_part_offset(io,"misc",0x800,mem,32,0x1000):
    - offset != 0, so it first dump_partition()s the WHOLE 1 MB misc into
      <path>/misc (a full read that must succeed byte-exactly),
    - fseek to 0x800, fwrite the 32 bytes,
    - load_partition_unify() -> load_partition("misc", file, step),
      which sends BSL_CMD_START_DATA with the whole 1 MB length and writes
