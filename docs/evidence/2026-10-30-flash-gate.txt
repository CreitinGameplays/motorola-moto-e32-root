So it is not a partition policy and not an image-content check: with
`secure: true` (fuse-anchored secure boot) the download path always requires a
Motorola/ODM signature that we do not have. Note the pattern: the data transfer
("Sending") is acknowledged, the *write* is refused.

--------------------------------------------------------------------------------
4. Why this matters: there is no restore path either
--------------------------------------------------------------------------------
`fastboot boot` does not execute anything (docs/evidence/
2026-10-30-fastboot-ram-boot-dead-end.txt) and `fastboot flash` is refused, so:

  - writing boot_b from a rooted Android with dd would be a ONE-WAY trip:
    if the new kernel does not boot, adb is gone, the fastboot write gate is
    still in force and there is no way to put the stock image back;
  - `adb reboot download` does NOT enter Unisoc download mode - the phone
    rebooted straight back into Android (adb device present, VID_18D1);
  - `fastboot set_active a` is not a clean fallback: slot _a carries an older
    kernel (Linux 4.14.199+-abc1989, built 2024-01-23, xscm@ontimbjlx014) and
    different vbmeta_system / vbmeta_vendor / vbmeta_product hashes.
