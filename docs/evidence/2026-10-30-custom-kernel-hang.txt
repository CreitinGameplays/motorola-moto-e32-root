# Custom kernel: secure world defeated, kernel-side hang (2026-10-30)

Companion to `2026-10-30-custom-kernel-a0-6.txt` (the rejection) and
`../11-flash-gate.md` (the gate). This file records the **successful** boot of
the self-signed image, and the start of the kernel-side diagnosis.

Symptom change is the whole point:

| `boot_custom_avb.img` (67,108,864 B) | same payload + self-signed vbmeta + AVB footer | boots **past** the secure world, then **hangs at the Motorola logo** |

## 2. Why the kernel hangs is still unknown

No adb, no fastboot, no reboot loop. `sysdumpdb` (`/dev/block/sda58`) holds only
an **older** dump - `2026-10-29 17:24:36`, `Native hang monitor trigger` ->
`panic` -> `sysdump_panic_event` - and nothing from this attempt. The hang
monitor needs `hang_detect_timeout` (2 min, `WAIT_BOOT_COMPLETE`) and only
starts at `module_init`, so a very early death produces no dump and no reboot.

The kernel console goes to a UART we cannot read, and `# CONFIG_VT is not set`
so there is no framebuffer console.

### Correction: we do not need to add a ramoops region

An earlier hypothesis was "ramoops must be patched into the DTB". That is
**wrong** - it is already there, in the stock DTB that both stock and our image
carry.

DTB extracted from the boot image (`artifacts/kernel-build/boot_dtb.dtb`,
175,402 B, FDT at file offset `0x20f2040`, tot size `0x2ad2a`; the "176 KB
trailer" *is* the DTB, not an opaque AVB template):

```
reserved-memory {
    ramoops@fff80000 {
        compatible = "ramoops";
        reg = <0x00 0xfff80000 0x00 0x40000>;
        record-size  = <0x8000>;
        console-size = <0x8000>;
        pmsg-size    = <0x8000>;
    };
};
memory@80000000 { reg = <0x00 0x80000000 0x02 0x00>; };   /* 8 GiB window */
```

And on the running stock device the driver really does bind
(`scripts/device/probe_ramoops.sh`):

```
/sys/bus/platform/devices/fff80000.ramoops          <- ramoops probed OK
/proc/device-tree/reserved-memory/ramoops@fff80000  <- node present, no no-map
ylog:: pstore /sys/fs/pstore pstore rw,... (mounted)
```

yet `/sys/fs/pstore` is empty. So pstore is configured, bound and mounted - the
missing piece is **DRAM persistence**, not DT plumbing.

Consequences for the next attempt:

- A **cold** power cycle (holding Volume Down / power from an off state) wipes
  DRAM, so nothing survives. Every recovery so far was cold, which explains the
  empty pstore.
- To capture the hang we need a **warm reset** while the log buffer is still in
  DRAM - i.e. the device must reset itself (watchdog/panic), or we must be able
  to trigger one. A hard hang gives neither.
- The region also lacks `no-map`; adding `no-map` (and optionally
  `no-dump-oops`/ECC tweaks) to the existing node is a cheap, low-risk DTB edit
  worth testing, but it is not what makes records appear.

## 3. Diagnosis plan: turn the hang into a panic

The hang is silent because nothing ever calls `panic()`. On this device a
*panic* is observable in two independent ways, a hang is not:

| channel | needs | survives |
|---|---|---|
| `sysdumpdb` partition | `panic()` -> `sysdump_panic_event` -> U-Boot writes the minidump | a cold power cycle (it is on eMMC) |
| `/sys/fs/pstore` | `panic()` -> pstore -> ramoops | a **warm** reset only (DRAM) |

The sysdump path is the reliable one, and it is set up earlier than expected:

- `early_initcall(sysdump_early_init)` registers the panic notifier
  (`drivers/soc/sprd/debug/sysdump/sysdump.c:1639`), i.e. before essentially
  every driver initcall.
- `minidump_info_g` is *statically* initialized with the section table,
  including a `log_buf` entry, and `prepare_minidump_info()` resolves it at
  panic time via `section_info_log_buf()` -> `log_buf_addr_get()` /
  `log_buf_len_get()`. So the kernel printk ring buffer is captured.
- `CONFIG_PANIC_ON_OOPS=y` and `CONFIG_PANIC_TIMEOUT=5`: a panic reboots by
  itself after 5 s, and that reset is a PSCI reset (warm), so ramoops also
  survives it.
- The BCB `tries_remaining` counter decrements on each failed boot, so after a
  few panic-reboot cycles U-Boot gives up on slot a and boots stock slot b on
  its own.

What is missing is only a *detector*: `# CONFIG_SOFTLOCKUP_DETECTOR is not set`.
The softlockup watchdog is what converts "CPU spinning forever" into
`BUG: soft lockup - CPU#0 stuck for 22s!` plus a full backtrace, and with
`softlockup_panic=1` into a panic. It is armed in `lockup_detector_init()`
(`init/main.c:1105`, just before `rest_init()`), so it covers the whole initcall
sequence.

Diagnostic build (`Image.slpanic`), identical to the hanging kernel except:

```
CONFIG_SOFTLOCKUP_DETECTOR=y
CONFIG_BOOTPARAM_SOFTLOCKUP_PANIC=y          -> 1
CONFIG_DETECT_HUNG_TASK=y
CONFIG_BOOTPARAM_HUNG_TASK_PANIC=y           -> 1
CONFIG_DEFAULT_HUNG_TASK_TIMEOUT=60
CONFIG_PANIC_TIMEOUT=5                       (unchanged)
```

No cmdline change is needed (the values come from `CONFIG_*_VALUE`), which
matters because the stock cmdline is `console=ttyS1,115200n8 buildvariant=user`
and rewriting it would risk dropping bootloader-supplied arguments.

The diagnostic kernel also carries one deliberate extra hunk
(`patches/kernel-sprd/diag-only-panic-after-init.patch`, compiled in only with
`KCFLAGS=-DDIAG_PANIC_AFTER_INIT`): a `panic()` at the very end of
`kernel_init()`, after `free_initmem()` and just before `run_init_process()`.

Reason: "hangs at the logo, no adb, no fastboot" has a second explanation that
fits perfectly - **the kernel boots fine but display and USB never come up**,
because the vendor modules were built against the shipping tree (125/282
`__crc_` mismatches for `mali_kbase.ko` alone). In that case the phone would
look dead while Android actually runs. A panic at the end of init separates the
two hypotheses within the same boot:

| observation | meaning |
|---|---|
| dump appears, reason `DIAG: kernel init complete` | all initcalls finished: the kernel is healthy, display/USB is the problem |
| dump appears, reason `BUG: soft lockup` + backtrace | the kernel really stalls, and the backtrace names the function |
| no dump, device sits still | stall with IRQs masked or before `rest_init()` |

Expected sequence, no manual intervention required:

```
boot slot a -> kernel hangs -> 20-40 s -> soft lockup -> panic()
            -> sysdump prepared, panic timeout 5 s -> reset
            -> U-Boot sees the dump request -> writes sysdumpdb
            -> tries_remaining decrements -> after N cycles boots slot b
```

Then: root the device, `scripts/device/dump_sysdump_full.sh`, pull
`sysdumpdb_full.img`, and run `scripts/host/sysdump_extract.py` - which prints
the crash banner, every `soft lockup` / `Call trace` / `PC is at` line, and the
whole recovered kernel log.

Limitation worth knowing: a softlockup is only detected while interrupts are
*enabled*. If the hang is a spinlock deadlock with IRQs masked, the detector
cannot fire; `DETECT_HUNG_TASK` then only helps for tasks stuck in D state.

## 4. Result of the diagnostic boot: no panic, and now we know why that is not conclusive

`boot_diag_avb.img` (kernel `Image.diag`, sha256 `b2d03818...215a`, image
sha256 `50e8fff4...c69900`) was written to `boot_a` (readback verified, sha256
matched), slot `a` set active, and booted. Result:

| detector armed | observed |
|---|---|
| `SOFTLOCKUP_DETECTOR` + `BOOTPARAM_SOFTLOCKUP_PANIC` | no `BUG: soft lockup` |
| `DETECT_HUNG_TASK` + `BOOTPARAM_HUNG_TASK_PANIC` | no hung-task report |
| `panic()` at the end of `kernel_init()` | never reached (or reached and invisible) |
| `PANIC_ON_OOPS` + `PANIC_TIMEOUT=5` | **no reboot at all** |

The device sat on the Motorola logo until it was power cycled by hand.

**The absence of a reboot proves much less than it looks.** Reading the actual
reset path in this tree:

```c
/* kernel/panic.c, CONFIG_SPRD_EMERGENCY_RESTART=y */
void sprd_emergency_restart(char *cmd)   /* called instead of emergency_restart() */
{
        if (cmd != NULL && strstr(cmd, "tospanic"))
                machine_restart("tospanic");
        else
                machine_restart("panic");
}
```

and in `arch/arm64/kernel/process.c`:

```c
void machine_restart(char *cmd)
{
        local_irq_disable();
        smp_send_stop();
        if (efi_enabled(EFI_RUNTIME_SERVICES)) efi_reboot(...);
        if (arm_pm_restart) arm_pm_restart(reboot_mode, cmd);
        else               do_kernel_restart(cmd);     /* restart_handler_list */
        printk("Reboot failed -- System halted\n");
        while (1);
}
```

**Correction (measured on the live stock device, this session): PSCI is present.**
The `psci` node is not in the kernel's own DTB section - the bootloader merges it
from the DTBO (`merge_dtbo : offset = 0x20 size=0xc9d9`), which is why parsing
`boot_dtb.dtb` missed it. Stock `dmesg` says:

```
psci: probing for conduit method from DT.
psci: PSCIv1.0 detected in firmware.
psci: Using standard PSCI v0.2 function IDs
CPU: All CPU(s) started at EL2
```

and a deliberately triggered panic (`echo c > /proc/sysrq-trigger`) **rebooted
the phone in 19 s**. So `machine_restart()` -> PSCI works, on stock and on any
kernel that gets that far. The earlier "no reset handler" theory is dead.

That leaves the real explanation, and it is the one this vendor platform
produces (see `mu300-linux` §31m for the same behaviour on a T760):

> the whole SoC stops, the way it does on a bus access that never completes -
> no soft or hard lockup report, no hung-task report, no panic.

A stopped SoC cannot panic, so no reset and no dump: exactly what was observed.
`el2_setup` installing the hyp stub unconditionally (no `CONFIG_KVM`
conditional) stays true and is not the cause.

### The watchdog: armed, but only late (correction, measured this session)

An earlier note here said no watchdog is ever armed. **That was wrong.** It
came from looking at `/sys/class/watchdog`, which is empty, and at
`watchdogd`. Both are true, but they do not mean the hardware is unarmed:

```
/sys/class/watchdog/                       (empty)
644e0000.watchdog -> bound to sprd-wdt-fiq (probe ran)
watchdogd: Failed to open /dev/watchdog    (no char device)
```

`sprd_wdt_fiq_probe()` never calls `watchdog_register_device()`, so there is no
`/dev/watchdog` - but a second piece of the same vendor block does the arming
directly, through the exported `sprd_wdt_fiq_get_dev()`:
`drivers/soc/sprd/debug/hang_debug/sprd_wdf.c` ("hardware watchdog feeder code
for Phoenix II", `late_initcall(sprd_hang_debug_init)`). On the live stock
device it is running:

```
/proc/sprd_hang_debug/wdf_timeout
WDF: interval=8 pretimeout=20 timeout=40 bitmap=0x00000000/0x000000ff
root 198..205  [hang_debug/0] .. [hang_debug/7]   (SCHED_FIFO per-CPU threads)
```

So on this firmware the AON watchdog **is** armed, at **40 s**
(pretimeout 20 s), and fed every 8 s (`timeout/5`) once all 8 CPUs have checked
in. That is `obj-$(CONFIG_SPRD_HANG_DEBUG) += debug/hang_debug/` in
`drivers/soc/sprd/Makefile`, and `CONFIG_SPRD_HANG_DEBUG=y` is in the stock
config *and* in every build of ours, so the mechanism is present in our kernels
too.

Two consequences, and they matter more than anything else in this document:

1. A hard stop **after** `sprd_hang_debug_init` (late_initcall, ~1.6 s; stock
   `dmesg` has `sprd_wdh: func_addr = ...` at 1.637 s) resets the board by
   itself after 40 s. The pmic path is irrelevant: `androidboot.wdten=0` makes
   `sprd_pmic_wdt` send `watchdog rstoff` (it wants the magic `e551`), but the
   AON watchdog covers the same job.
2. **Our diagnostic kernel hung for minutes without a reset.** It contains the
   same feeder (`CONFIG_SPRD_HANG_DEBUG=y`), so it must have stopped **before
   late_initcalls** - i.e. before roughly 1.6 s into the boot, in the
   `early`/`core`/`device` initcall range or earlier than `start_kernel`'s
   `rest_init()`. That is a much tighter window than "somewhere before
   userspace", and it puts `kvm_arch_init()` (device_initcall, from
   `virt/kvm/kvm_main.c`) squarely in the frame.

Also note the device name claimed by the bootloader: `androidboot.hardware=ums9230_4h10`,
`androidboot.auto.chipid=UMS9230-AB`, i.e. the T606 reports as UMS9230.

### The reset hardware that does not need a handler

From the stock DTB (811 nodes parsed from `boot_dtb.dtb`):

| node | compatible | meaning |
|---|---|---|
| `/soc/aon/watchdog@644e0000` (`size 0x10000`) | `sprd,wdt-r2p0-fiq` | AON watchdog, hardware reset, no PSCI and no driver needed |
| `/soc/aon/spi@64200000/pmic@0/watchdog@40` | `sprd,sc2730-wdt`, `sprd,sc27xx-wdt` | SC2730 PMIC watchdog - resets PMIC/AP/modem together |
| `/soc/aon/spi@64200000/pmic@0/hw_reset@1bc0` | `sprd,sc2730-7sreset` | PMIC-level "7 s reset" |

`drivers/watchdog/sprd_wdt_fiq.c` gives the AON register map for that node:
`LOAD_LOW 0x0`, `LOAD_HIGH 0x4`, `CTRL 0x8`, `LOCK 0x20`,
`UNLOCK_KEY 0xe551`, `CNT_STEP 32768`, `CNT_EN = BIT(1)`, `RST_EN = BIT(3)`.
Programming LOAD/CTRL directly from early C yields a **self-reset that survives
a hard lockup**, which is exactly what is missing from the diagnostic build.

### The device is Virtual A/B: slot a has no userspace (measured 2026-10-30)

This is the single most important platform fact found so far, and it invalidated
part of the test plan.

```
$ getprop ro.virtual_ab.enabled
true

$ lpdump            # super metadata
Slot 1:
Metadata version: 10.2
Header flags: virtual_ab_device
  Name: system_b          Group: group_unisoc_b   Attributes: readonly,updated
  Name: system_ext_b      ...
  Name: vendor_b          ...
  Name: product_b         ...
  Name: system_b-cow      Group: cow
```

There is exactly **one** set of dynamic partitions, and they are all `_b`.
`system_a`, `vendor_a`, `product_a` **do not exist** - `super` has no extents for
them. Slot `a` therefore has a kernel (`boot_a` is a real 64 MiB partition) but
**no Android userspace to boot into**.

Consequence, measured end to end:

1. `boot_stock_signed.img` (an unmodified **stock** kernel in our AVB-signed
   container) was written to `boot_a`, `fastboot set_active a`, reboot ->
   **bootloop**.
2. That loop is `init` failing to mount `system_a`/`vendor_a`, panicking, and
   `panic_timeout=5` + PSCI resetting into the same slot again.
3. So the loop is *not* a container/AVB/`dd` failure. On the contrary, it proves
   the container path works: the stock kernel started far enough to run
   `init`.
4. `sys.boot.reason.history` after recovery:
   `bootloader,1793380176 / bootloader,1793379979 /
   kernel_panic,sysrq_trigwarmd_crash,1793379216`.

Practical consequences:

- Booting slot `a` can never reach Android, so **no kernel can be judged by
  "does Android come up" on slot `a`**. Only the pre-`init` window is testable
  there - which happens to be exactly where our kernel dies, so `boot_a` tests
  remain valid for the *watchdog/stall* question but say nothing about
  userspace.
- The only slot whose userspace can boot is **`b`**, and `boot_b` is off limits
  (fallback). Do not write it.
- `set_active a` is therefore **not** a safe recovery mechanism; it produces an
  intentional bootloop. Recovery is `set_active b` (verified twice).
- The remaining clean channel is `fastboot boot <image>`, which loads a kernel
  into RAM without writing any partition. If this bootloader supports it, it is
  both the test mechanism and a zero-risk one. It is the next thing to try.
- Also note `system_b-cow`: a COW snapshot of `system_b` exists and the `_b`
  partitions carry the `updated` attribute, i.e. an OTA snapshot was applied at
  some point. Harmless for us, but it means b's userspace is a snapshot merge
  result, and it is the userspace that must be kept.

### The panic channel is proven, end to end

The deliberate `sysrq-c` panic on stock also shows the channel we would use is
fully working:

| evidence | content |
|---|---|
| `/sys/fs/pstore/dmesg-ramoops-0` | 54,565 B, begins `Panic#1 Part1`, contains the whole ring buffer |
| `/sys/fs/pstore/console-ramoops-0` | 3,290 B: `Kernel panic - not syncing: sysrq triggered crash` -> `sprd-sysdump: (sysdump_panic_event)` -> `Sysdump enter, preparing debug info to dump ...` -> `reason: sysrq triggered crash` |
| reset | PSCI, device back on adb after 19 s |

Copies: `artifacts/pstore-proof/`. So **a panic is fully observable** on this
device: ramoops text plus a `sysdumpdb` write. What was missing was a panic, not
a channel.

The pstore record also gives the timings that matter: `run init` at 2.048 s, the
minidump section table (`section_info_log_buf ... len: 0x100000`) at 1.893 s - so
a panic anywhere after ~1.9 s captures the 1 MiB kernel ring buffer.

### DIAG build v3: arm the watchdog earlier than the feeder does

The vendor feeder already arms the AON watchdog, but at `late_initcall`. Our
kernel dies before that, so the useful question became *where*, and the only
way to answer it is to have a watchdog that is already running before the
stall. The DIAG patch
`patches/kernel-sprd/diag-only-arm-aon-watchdog.patch`
(`KCFLAGS=-DDIAG_WDT_ARM`) arms it inside `sprd_wdt_fiq_probe()` right after
`sprd_wdt_fiq_enable()` has the clocks and the new-version bit up:

```c
wdt->wdd.timeout = 30;
sprd_wdt_fiq_set_timeout(&wdt->wdd, 30);
sprd_wdt_fiq_start(&wdt->wdd);     /* CNT_EN | INT_EN | RST_EN */
```

**Correction, measured 2026-10-30: this arm can never fire before KVM init.**
The earlier reasoning ("the probe is a `device_initcall`, link order puts
`drivers/` before `virt/`, so the arm lands ahead of `kvm_init()`") is wrong
about the level. In `drivers/watchdog/sprd_wdt_fiq.c` the driver is *not*
registered by `module_platform_driver()`; it is registered explicitly:

```
474: late_initcall(sprd_wdt_fiq_init_ops);
```

So `sprd_wdt_fiq_probe()` is a **`late_initcall`**, and it runs *after* every
`device_initcall` - including `kvm_init()`, which is `module_init()` in
`virt/kvm/kvm_main.c`. Link order only breaks ties *within* one level; it
cannot reorder across levels. A stall inside `kvm_init()` therefore happens
before the probe, the 30 s arm never executes, and the SoC never resets.

Measured, and it matches exactly: `boot_diagwdt_avb.img` written to `boot_a`
(`ca3caec0...9d61`), `set_active a`, reboot ->
**stuck on the Motorola logo for several minutes, no reset, no adb, no fastboot.**
That is the "no reset" row of the table below, and it is the row that means
*the stall precedes the wdt probe* - not that KVM is innocent, but that the arm
is behind KVM rather than ahead of it.

Consequence for the design: the arm has to be *earlier than* `kvm_init`, or
`kvm_init` has to be *later than* the arm. The cheap, hardware-free option is
the second: move `kvm_init()` from `module_init` to `late_initcall` in
`virt/kvm/kvm_main.c`, so both are `late_initcall`s and the normal link order
(`$(drivers-y)` before `$(virt-y)`) puts the wdt probe first. Then a KVM hang
is reset by our own 30 s arm.

Outcome table for this image, against the feeder's own 40 s:

| observation | meaning |
|---|---|
| **no reset for minutes** (measured) | stall is **before** the `late_initcall` probe that arms the timer - the arm is simply too late |
| reset + dump, log ends in `kvm_init` | v4 ordering works and KVM init is confirmed |
| no reset, while `boot_diagstock_avb.img` (same tree, KVM off) resets or boots | the stall is in our tree/build, not KVM |

Recovery after a slot-`a` failure is better than first assumed, and this was
measured: a slot-`a` boot that **panics** does not loop forever. The bootloader
retries a few times and then parks itself in **fastboot** on its own
(`reset_mode: (4)-(fastboot)` in its log). Observed on 2026-10-30: after the
slot-`a` attempt the phone sat in fastboot without anyone touching it, and
`persist.sys.boot.reason.history` had grown four consecutive `bootloader,...`
entries. From fastboot, `set_active b` is a one-command recovery.

Caveat that still holds: that self-recovery relies on the kernel **resetting**.
A *hard hang* (whole SoC stopped, no reset) is not covered by it - the phone
would sit on the logo until a manual power cycle. That asymmetry is exactly why
an early-armed watchdog is the goal.

### Three candidate test channels, and what happened to each (2026-10-30)

**1. `fastboot boot <image>` - ruled out, it is a no-op on this bootloader.**

It answers `OKAY` and the phone reboots, but it boots the **active slot** and
ignores the payload. Proof, not assumption: the stock kernel was extracted from
`boot_b`, five occurrences of its version string were patched `4.14.199+` ->
`9.99.999+` (same length, so the image stays structurally identical), the image
was repacked and AVB-signed (`boot_banner.img`,
sha256 `6c3150da...0f3b`), and `fastboot boot` it. Result: `/proc/version`
still reported `4.14.199+`, and none of the image's own cmdline tokens
(`diagmarker=fastbootboot`) appeared in `/proc/cmdline`. `boot_a` and `boot_b`
hashes were unchanged afterwards, so nothing was written - it simply loaded
nothing. `fastboot boot` is dead as a channel.

**2. Booting slot `a` - works, but only for the pre-`init` window.**

Established earlier: stock kernel on slot `a` reaches `init`, `init` cannot
mount `system_a`, panics, resets. So the container, the AVB signature and the
`dd` write are all proven good, but slot `a` can never reach Android. Useful
for exactly one question - what happens in the first ~2 s - which is
unfortunately the question we have.

**3. Append `androidboot.slot_suffix=_b` to the boot-image cmdline - does not
work; boot-image cmdline is not honoured at all.**

Idea: Android `init` takes the *last* `androidboot.slot_suffix=` token, so a
kernel booted from `boot_a` could be told to mount slot `b`'s real userspace
and the test slot would stop being a dead end. Built `boot_suffixb.img` (stock
kernel + `androidboot.slot_suffix=_b diagmarker=suffixb`,
sha256 `9ae277c0...4f58`), `dd`-wrote it to `boot_a`, verified the readback
hash, `set_active a`, rebooted.

Result: the phone went back to **fastboot** on its own (user-confirmed twice,
without touching it). It did not come up on Android, and afterwards
`/proc/cmdline` on slot `_b` contains `androidboot.slot_suffix=_b` exactly once
-i.e. still only the bootloader's own token - and no `diagmarker` anywhere.
Combined with the `console=ttyS1,115200n8` -> `console=null` replacement, the
conclusion is: **the boot image's cmdline field is discarded**; the kernel
cmdline is assembled by the bootloader (largely out of the DTB `/chosen`
node, cf. `kernel/printk` suppression and `androidboot.*` tokens). Editing the
boot header's cmdline cannot change how the kernel is booted. Only `<= 64`
bytes of `dtb`-section or kernel-side changes remain -i.e. a rebuilt dtb, or a
kernel that ignores the cmdline.

State left behind: `boot_a` = `boot_suffixb.img` (harmless, slot `a` is not
bootable anyway); `boot_b` untouched at `ccd0faff...7b18`; Android running on
`_b`, `sys.boot_completed=1`.

**4. `fastboot flash` - still refused.**

`fastboot flash boot_a <stock boot_b backup>` ->
`(bootloader) Please verify the signature!` / `FAILED (remote: 'Please verify
the signature!')`. So the bootloader's flash path enforces *its* signature
(not our AVB key), while the `dd` path with our own AVB footer is accepted and
boots. This is also why `boot_b` cannot be restored through fastboot: the only
way in is `dd` from a live Android, which is circular. `boot_b` stays
hands-off.

## 5. Other facts confirmed this session

- Boot image header is equivalent in stock and custom: page 2048, header v2,
  `os_version 0x16000182`, `kernel_addr 0x8000`, `ramdisk_addr 0x5400000`,
  kernel = valid ARM64 `Image` (magic `ARMd`, `text_offset 0x80000`,
  `flags 0xa`, `image_size 0x1b29000`).
- The stock cmdline lives at header offset `0x40` (the `name` field at `0x30`
  is empty, which is why early probes reported an empty cmdline):
  **`console=ttyS1,115200n8 buildvariant=user`** - the console is UART1, which
  is why nothing reaches USB/adb.
- The DTB is a v2 `dtb` section: `dtb_size 175466`, loaded to
  `dtb_addr 0x1f00000`, at file offset `0x20f2000`. The FDT magic starts 0x40
  bytes into that section. Packing must copy the *whole section*, not just the
  FDT, to stay faithful to stock.
- Address budget: kernel load `0x8000` + stock `image_size 0x1b29000` ends at
  `0x1b31000`; the DTB is at `0x1f00000` and the ramdisk at `0x5400000`, so
  there is ~3.5 MB of slack. A slightly larger kernel does not collide.
- `scripts/host/pack_and_sign_boot.py` repacks any `Image` into the stock
  container and AVB-signs it; a round-trip with the stock kernel reproduces the
  stock payload region byte-for-byte (only the informational SHA-1 `id` field
  differs, and the bootloader does not validate it - the earlier custom image
  booted with a recomputed one).
- Build config vs stock `/proc/config.gz`: exactly 2 value deltas
  (`CONFIG_VIRTUALIZATION`, `CONFIG_VSOCKETS`) plus 24 derived KVM/VHOST
  symbols. No config drift, so the hang is not a config problem.
- Remaining known mismatch: vendor `mali_kbase.ko` has 125/282 `__crc_`
  mismatches against the built kernel, so even a successful boot would not load
  the GPU module.
- `CONFIG_SPRD_SYSDUMP=y`, `CONFIG_SPRD_NATIVE_HANG_MONITOR=y`,
  `CONFIG_SPRD_HANG_DEBUG=y`; `# CONFIG_SPRD_DEBUG is not set`.
- The bootloader reports the SoC as `androidboot.hardware=ums9230_4h10`,
  `androidboot.auto.chipid=UMS9230-AB` (the T606 is a UMS9230 variant), and
  `cpu: T606 AB` over fastboot.
- `androidboot.wdten=0` and `sysdump_magic=80001000 sysdump_re_flag=1` are part
  of the bootloader cmdline; `modem=shutdown`, `loglevel=1`,
  `console=null` (the UART console is only reachable at 115200 8N1 on UART1).

## 6. External reference for this exact signature

`dikeckaan/mu300-linux`, `docs/FINDINGS.md` (ZTE F50 / MU300, Unisoc T760,
Sept-Oct 2026) - same vendor family, modern kernels:

- **31m, "Hard hangs in the first seconds"**: "In both, the heartbeat stops
  together with the kernel log: no soft or hard lockup report ... no
  hung-task report ... no panic. The whole SoC stops, the way it does on a bus
  access that never completes. The PMIC watchdog (procd: 30 s) then resets the
  board." - exactly our symptom, and the reason lockup detectors are useless
  here. Also: "After the PMIC watchdog's reset, LK sees `hw watchdog rst int
  pending` and goes into `sprd_sysdump`: a minidump plus a zlib-compressed full
  RAM dump". That is how a *watchdog* reset becomes a readable dump.
- **5, "The ~290 s power cut (PM co-processor watchdog)"**: `sprd_pmic_wdt`
  disarms the PM co-processor watchdog by sending `watchdog rstoff` over an
  SIPC sbuf channel; the channel is only ready after `pm_sys` is reloaded.
- **3, "Logs without a serial console"**: pstore survives only a warm reset,
  and their failures mostly end in a power cut; they persist stage markers into
  spare space in a boot partition instead - a channel we do not have, since our
  AVB image fills the whole 64 MiB partition.
- **31d**: `softlockup_panic`/`hardlockup_panic` have nothing behind them
  unless the detectors are built in; `sysrq-c` -> panic -> pstore is the
  self-test we reproduced above (ours rebooted in 19 s).
- **31o**: the firmware starts every CPU at EL2 on their boards too
  (`CPU: All CPU(s) started at EL2`), and KVM works there (5.4 nVHE, 6.18 VHE),
  so "KVM at EL2" is not by itself a problem on this platform.
