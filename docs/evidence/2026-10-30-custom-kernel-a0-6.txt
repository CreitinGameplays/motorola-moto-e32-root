# 2026-10-30 - custom kernel written to boot_a: rejected with a0=6

Goal: boot the locally built kernel (`4.14.199+-ab612c2`,
`artifacts/kernel-build/boot_custom.img`) by writing it to the *inactive* slot
`boot_a` from rooted Android and switching slots with `fastboot set_active a`.
Stock `boot_b` was never written.

Recovery was already proven (see `2026-10-30-slot-switch.txt`), so the only
irreversible part was the write to `boot_a`, which was approved.

## 3. Result: boot loop, rejected before AVB

The phone boot-looped (Motorola logo, no adb, no fastboot). Volume Down
brought up fastboot; `fastboot set_active b` + reboot restored Android on
`_b` (`ab612c2`) and `mali_kroot` regained root on the first attempt.

The bootloader log (`uboot_log`, 4 MiB, 32 x 128 KiB blocks) records each
attempt. Dump: `artifacts/slot-probe/uboot_log_after_a.img`
(sha256 `d6de51ede2c7be9fae47ec89ebce173a619e5c4e0494c7b3f8f256bc8c9e6f96`).

Three slot-a attempts (boot counts 148/149), each ends with:

```
[00004454] uboot_vboot_verify_img() return error:param->a0=6
[00004461] boot count 149
```

| 16/20/22 | `_a` | 0 | 65534 | **none at all** | `a0=6` |

The failing slot-a boot has the *same* `img_ver` table and the same

and `a0=6`: U-Boot's own libavb never even starts. So the rejection happens
inside the secure world, in the SIP call made just before it.

## 5. Where a0=6 comes from

`uboot_vboot_verify_img()` is a SIP trampoline (VA `0x9f08cedc`):

```
9f08ceec  mov  w0, #0x20          ; FUNCTYPE 0x20
9f08cef0  mov  w1, x3            ; ctx
9f08cef8  bl   #0x8d0e8          ; smc #0
9f08cefc  ldr  w1, [x0]          ; a0 = *result
9f08cf04  cbz  w1, #0x8cf1c
9f08cf08  adrp x0, #0xd6000 ; 'uboot_vboot_verify_img() return error:param->a0=%d'
9f08cf14  mov  w0, #2            ; reset reason
9f08cf18  bl   #0x3c6fc          ; reboot
```

There is **no tolerance in the wrapper**: any non-zero `a0` reboots.
The `cmp #5` tolerated-result logic lives in the callers, and only *after* a
successful SIP call:

```
9f0820d4  bl   #0x8cedc           ; verify the boot partition
9f0820e4  ldr  w20, [x0]          ; result word
9f082124  ldr  w0, [x23, #0x768]  ; lock state
9f082128  cmp  w0, #1
9f08212c  b.ne #0x8213c
9f082134  mov  w1, #2             ; locked  -> state 2
9f08213c  cbnz w20, #0x82148
9f082140  str  w20, [x0, #0x810]  ; result 0 -> state 0
9f082148  cmp  w20, #5
9f08214c  mov  w1, #1
9f082150  b.eq #0x82158           ; result 5 -> state 1 (orange, still boots)
9f082154  mov  w1, #3             ; anything else -> state 3 (fail)
```

`0` = OK and `5` = tolerated are exactly the first two values of
`AvbSlotVerifyResult`, and `u-boot`'s caller stores them as verified-boot
states 0 and 1.

## 6. a0=6 is AVB *invalid metadata*, not a bad signature

`trustos_b.img` contains its own copy of libavb, with the verdict enum as
strings:

```
0x092d98  ERROR_VERIFICATION
0x092db0  ERROR_ROLLBACK_INDEX
0x092de8  ERROR_INVALID_METADATA
0x092e00  Unknown AvbSlotVerifyResult value.
0x093e20  >>>>>>>>>>>>>>>>  avb_slot_verify result is %d.
0x0942b0  vboot_verify_ret is %d, key_istrusted:%d.
0x094820  [kbc]avb_check_kbc_image() ...
```

`AvbSlotVerifyResult` is:

```
0 OK
1 ERROR_OOM
2 ERROR_IO
3 ERROR_VERIFICATION
4 ERROR_ROLLBACK_INDEX
5 ERROR_PUBLIC_KEY_REJECTED
6 ERROR_INVALID_METADATA
7 ERROR_UNSUPPORTED_VERSION
8 ERROR_INVALID_ARGUMENT
```

So `a0=6` = **ERROR_INVALID_METADATA**, and the tolerated `5` is
**PUBLIC_KEY_REJECTED** - the result an *unlocked* device is supposed to
return for a vbmeta it cannot chain to the OEM key. That is the intended
escape hatch: libavb treats "unknown but well-formed key" as a warning when
`allow_verification_error` is set, and TrustOS/U-Boot accept it.

## 7. Why our image is "invalid metadata": it has no vbmeta at all

Stock vs custom layout (`page` = 2048, header version 2):

```
                    stock boot_a/b                    custom boot_custom.img
ANDROID! header      0x000000                          0x000000
kernel               0x000800                          0x000800
ramdisk             ...                               ...
payload end          0x020f2000                        0x0214d000
176128-B trailer     0x020f2000..0x0211d000            0x0214d000..0x02178000
vbmeta  'AVB0'       0x0211d000 (2304 B)              absent
zero padding         0x0211d900..0x03ffffc0            absent (file ends)
footer  'AVBf'       0x03ffffc0 (last 64 B)           absent
```

Details checked:

* the 176,128-byte trailer is **byte-identical** in stock `boot_a`, stock
  `boot_b` and our build (sha256 `dc92c62a3c5d188b560ca2f6735a2f7425f137af4fc6f00daec60f79ae5d84c6`).
  Stock a and b even differ in kernel content, so this trailer is a static
  template, not a per-image signature - keeping it is safe.
* boot headers are equivalent: `ANDROID!`, page 2048, header version 2,
  `os_version 0x05400000`, same `ramdisk_size`.
* stock `AVBf` footer: `original_image_size = 0x211d000` (payload + trailer),
  `vbmeta_offset = 0x211d000`, `vbmeta_size = 2304`, `SHA256_RSA4096`,
  rollback index 2, hash descriptor over partition `boot` with salt
  `f83b993601311bca149a573c1e737666ff011f6cf2aa2a5ae822f91b97af0991`.
* `avbtool info_image` on stock `boot_b.img` reports exactly that, plus two
  props (`com.android.build.boot.fingerprint`, `...os_version`).

`avb_slot_verify` on a partition whose footer magic is absent falls back to
reading a vbmeta struct at offset 0; there `ANDROID!` is not `AVB0`, so the
metadata is invalid -> `ERROR_INVALID_METADATA` (6). Consistent with the log.

## 8. Candidate fix (not yet tested)

Sign the custom image with a throwaway key and a correct AVB hash footer:

```
python scripts/host/build_avb_boot.py
  -> artifacts/kernel-build/boot_custom_avb.img
     67,108,864 bytes, sha256 eda3433fa18a65a9ac66287494c73db81d1c3da613e96f0e8a290e3d33e58dc3
     SHA256_RSA4096, rollback_index 2, vbmeta at 0x02178000, footer at 0x03ffffc0
     payload byte-identical to boot_custom.img
```

Expected secure-world result: the vbmeta is well-formed, hash descriptor matches
the image, so verification reaches the public-key check. Our key is not the OEM
key, so `validate_vbmeta_public_key()` fails -> `ERROR_PUBLIC_KEY_REJECTED` =
`a0=5`, which U-Boot maps to verified-boot state 1 and accepts.

Failure modes to watch in the next `uboot_log`:

| a0 | meaning | consequence |
|---|---|---|
| 0 | OK (key trusted) | boots - unlikely |
| 5 | public key rejected | **boots** - expected |
| 3 | verification | hash/descriptor mismatch in our build |
| 4 | rollback index | stored index > 2 |
| 6 | invalid metadata | footer/vbmeta still malformed |
| 7 | unsupported version | footer version/content issue |

  A full-partition write (`dd bs=1M`) of the rebuilt image removes that
