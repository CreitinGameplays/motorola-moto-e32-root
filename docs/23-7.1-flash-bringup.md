# 7.1 flash-based bring-up plan (2026-11-05)

Decision record + full-component audit for booting the mainline (7.1-rc1)
kernel via **flashing** instead of kexec. Companion evidence:
`docs/evidence/2026-11-05-kexec-*.txt`, research: `docs/22-kexec-hang-research.md`.

## 1. Why kexec is closed

Tests 9-16 (evidence files above, analysis in docs/22):

- Every jump from a boot older than ~5 min died silently. Test 13 proved
  the known-good 4.14 self-test image dies too (boot age is the variable,
  not the target image).
- Test 14's panic instrumentation caught one real killer: kexec's
  device_shutdown() oopses on the runtime-idle UFS host (ufshcd reset
  err 5 -> host reset -> ufshcd_intr completes into garbage -> panic in
  IRQ). `panic=5` converted that class into warm self-recovery.
- Tests 15/16 (UFS pinned awake + CPUs offlined + panic knobs on BOTH
  kernels) still hung silently: no oops, no panic, no return. With both
  panic paths armed, the death can only be in the panic-less windows:
  purgatory, the secure monitor, or the target's pre-printk code (bus
  deadlock class). Unobservable from Linux, and the earlier SMC-hang
  tests showed the monitor is hostile to kexec'd entries.
- Verdict: kexec is not a viable iteration channel on this device.

## 2. The new approach (community-proven)

The ums9230-mainline community (Jolla C2 / Reeder S19 Max Pro S, same
fork, same SoC, FOSDEM 2026) iterates by **flashing boot images** - and
debugs with **on-panel text/markers** (the bootloader leaves the display
scanning the logo buffer; the kernel paints into it). They chainload
U-Boot as a header-v4 boot image to escape the DTBO problem; that is the
likely long-term iteration environment for us too.

Our equivalent, using only proven device infrastructure:

1. Pack the 7.1 kernel + logsave initramfs + mainline DTB into a
   self-signed AVB boot image (`scripts/host/pack_and_sign_boot.py`).
2. Flash it to **boot_b** with **one-attempt slot arming**; boot_a rescue
   untouched (`scripts/host/run_boot_b_test.ps1`, all proven).
3. Log channels (independent, all survive every recovery except where
   noted):
   a. **The panel** - the 7.1 Image paints a 12-segment progress bar and
      a status grid from `head.S` pre-MMU (`include/linux/diag_stage.h`
      in the fork). Live, human-readable, survives everything.
   b. **sysdumpdb partition** - logsave /init dumps the whole kernel
      ring to sysdumpdb+0x100000 (backup copy at +0x200000) with the
      magic `H71LOG01`. Survives even a cold power hold.
   c. **pstore ring** - 7.1 has PSTORE_CONSOLE=y; survives warm resets
      (its content is also inside (b) once init runs).
4. The 7.1 boots -> logsave runs -> reboot -> bootloader sees slot b's
   try spent -> boot_a rescue restores stock boot_b -> Android.
   If the 7.1 hangs before init: power hold -> same fallback.
5. Restore the daily driver: from the rescue-restored stock Android,
   `mali_kroot` root, then `dd` the saved kexec/Magisk boot_b image
   (`artifacts/kernel-build/boot_kexec_414.img`) back, reboot.

## 7. The rendering bug: the scanout is a8r8g8b8/32bpp, stride 2880

(2026-11-05, evening) The on-panel rendering artifacts ("sheared rows,
repetitions, vertical white bars") had a single root cause: the painter
assumed RGB888/24 bpp with stride 2160, while the bootloader's DPU
scanout is **a8r8g8b8, stride 2880**.  Two independent sources agree:

- the fork's Reeder S19 Max Pro S DTS (same SoC, same LK generation)
  declares `simple-framebuffer` with `stride = <(720 * 4)>`,
  `format = "a8r8g8b8"`;
- the 2026-11-05 test-23 boot with the 32 bpp painter rendered
  correctly for the first time ("the artifacts were fixed" - user).

The 2026-11-04 conclusion "the buffer is RGB888" was premature: the
32-bit-pixel test back then kept the 2160-byte stride, which overflows
every 720-px row and shears the glyphs - the stride, not the pixel
size, was the error.  (The cmdline's `logo_bpix=24` describes the logo
BMPs in the logo partition, not the DPU layer format.)

Fixes applied to BOTH trees (`ums9230` fork and `kernel-sprd` 4.14):
stride 2880, 4-byte pixels `[B, G, R, A=0xff]` (alpha 0xff so the DPU
does not blend), the head.S pre-MMU macro geometry, and - for the 7.1 -
the framebuffer reservation enlarged 4 -> 8 MiB (the 32 bpp frame is
4.6 MiB; the old 4 MiB reserve left the bottom rows to the page
allocator, a second artifact source).

## 8. The simplefb earlycon (kernel text on the panel)

The mainline simplefb earlycon (Markuss Broks' v3 LKML series,
2022-12-21, never merged) was ported to the 7.1 fork:
`drivers/video/console/earlycon.c` + `CONFIG_FB_EARLYCON`.  Geometry
from the command line - no DTB changes, works with the vendor DTB:

    earlycon=simplefb,mmio,0x9e000000,720x1600x32 keep_bootcon

Gotchas measured on the way:
- the `mmio` token is REQUIRED: the earlycon core's parse_options()
  runs uart_parse_earlycon() first, and without an iotype token it
  bails before setting port->mapbase - the setup function then sees
  mapbase == 0 and returns -ENODEV (test 23 rendered nothing).
- the mappings are forced write-combine: the DPU fetches directly from
  DRAM and is not cache-coherent with the CPU.
- the 7.1's efi/earlycon.c could not be reused as-is (it reads the
  geometry from sysfb_primary_display/screen_info); the port keeps its
  x-coordinate cache and scroll logic.

## 9. Milestone dashes (the freeze-point instrument)

diag_milestone(n) paints one 12x10 dash per early-boot milestone
(row 110 below the status grid).  Mapping: 0 acpi_boot_table_init,
1 unflatten_device_tree, 2 bootmem_init, 3 kasan_init,
4 request_standard_resources, 5 setup_arch done, 6 setup_per_cpu_areas,
7 vfs_caches_init_early, 8 trap_init, 9 sched_init,
10 workqueue_init_early, 11 rcu_init, 12 init_IRQ, 13 tick_init,
14 hrtimers_init, 15 time_init (the boot watchdog arms here),
16 console_init, 17..24 initcall levels early..device.

Measured: the DRM-on build freezes at 17 dashes (early initcalls done;
the freeze is in the pure level or the SMP bring-up window), while the
DRM-off builds froze around milestone 4-5 - the DRM-off config change
is a real early-boot regression, cause still unknown.  The big-digit
variant of the counter rendered as huge vertical bars (the digit "1"
is a vertical bar at 160 px) and was removed after the 32 bpp fix made
the dash row readable.

## 10. Why every earlycon path failed, and the panel log console (test 28)

Test lineage of the "kernel text on the panel" attempts (all evidence in
`docs/evidence/2026-11-05-boot_b-tests.txt`):

- t23-25, cmdline earlycon (`earlycon=simplefb,mmio,0x9e000000,...`):
  **dead end**.  The Unisoc LK ignores the boot image cmdline entirely -
  it carries its own bootargs (found embedded in `uboot_a.img`,
  "console=null ..."), patches them into the DTB `/chosen/bootargs`, and
  strips the `earlycon` token while rewriting (the vendor DTB's static
  bootargs literally begin with `earlycon` - the LK removes it).
  `/proc/cmdline` never contains any image cmdline token.
- t26, `CONFIG_CMDLINE`: arm64's pi parser (`idreg-override.c`)
  does not dispatch generic `early_param` handlers, and with
  CMDLINE_FROM_BOOTLOADER the built-in generic params are ignored when
  the bootloader provides bootargs.  The build also died at entry
  reproducibly (no first paint) - cause unknown, reverted.  Dead end.
- t27, DT-node earlycon (`/chosen/framebuffer0` compatible
  "simple-framebuffer" + `/chosen/stdout-path`): registered nothing
  (markers legible, no text).  Suspects: stdout-path was a bare
  "framebuffer0" (an alias-less relative path, while
  `early_init_dt_scan_chosen_stdout` needs a full path or an alias), and
  our ported `fb_earlycon_setup` reads geometry only from the cmdline
  options string ("720x1600x32"), which a DT registration never
  provides.  Also moot: even when registered, DT earlycons cover only
  the window between the FDT scan and the real console.
- The pstore ring is empty for the 7.1 by construction: the freeze at
  m17 happens before the pstore/ramoops driver ever initializes, so the
  ramoops console never registers and the ring survives with the
  previous 4.14/rescue boot's tail only (the H71RING1 capture of test
  27 held "systemserver cmd" noise + the rescue's reboot line).

The definitive channel (test 28): **the panel log console** - our own
painter registered as a real printk console.  `diag_txt_puts` (a port
of the 4.14's proven text engine: 8x16 VGA font at 2x = 16x32 px
glyphs, 40 columns x 39 rows in panel rows 128..1532, below the
milestone dashes, above the mirrored bottom bar) becomes
`diag_console.write`, and `register_console(&diag_console)` with
`CON_PRINTBUFFER` runs at the END of `setup_arch()`:

- CON_PRINTBUFFER replays the ENTIRE log buffer first - messages
  printed before registration appear too, so nothing is lost.
- Not CON_BOOT, so no later console ever unregisters it.
- `.write` is serialized by the printk core - this is why a console
  driver is safe where the 4.14's `vprintk_emit` mirror was racy (the
  4.14 engine had printk mirroring deliberately disabled for exactly
  that race; its engine and `include/linux/diag_font.h` were reused).
- No cmdline, no DT node, no driver init: nothing the LK can strip and
  nothing the m17 freeze can skip (the text engine paints through the
  linear map right after `paging_init()`).

Console registration point: end of `setup_arch()` (after
`smp_build_mpidr_hash()`), where the milestone 5 is painted - i.e. the
console is live for everything from the initcall levels onward, which
brackets the m17 freeze.  Expected panel: dashes as before, then the
black text area below fills with the log; the last visible line at the
freeze names the bug.

## 11. Test 28 RESULT: the "m17 freeze" was a kernel panic, and its cause

The panel console worked immediately (user photo + OCR,
`docs/evidence/2026-11-05-7.1-test28-panic.txt`): the tail of the text
area was a single panic dump -

    Kernel panic - not syncing: Asynchronous SError Interrupt
    ... el1h_64_error ... hawaii_wdt_arm+0xb4 (P)
    kernel_init_freeable+0x33 ... kernel_init+0x20 ... ret_from_fork

Facts resolved by it:

- The "17 dashes" were milestones m0..m16 (last painted: console_init)
  - the count was misread as "m17 done" all along.  The death point is
  the FIRST statement of `kernel_init_freeable()`: our
  `hawaii_wdt_arm(hawaii_wdt_timeout)` re-arm - the only call site.
  (The m15 hook `hawaii_boot_progress("early")` arms only the software
  deadline + heartbeat timer, not the AON WDT.)
- The trace shows a nested exception (an `el1h_64_sync` entry frame
  under the error entry): the aborting access took a synchronous
  external abort and the SError won the race during entry.  The
  aborting instruction (vmlinux disassembly, +0xb4) is the WDT RTC-sync
  poll READ of base+0x10 inside the inlined `hawaii_wdt_load` wait
  loop; the earlier UNLOCK/LOAD writes are swallowed by the bus bridge.
- Root cause: the AON watchdog's two `aonapb_gate` clocks are OFF in
  early boot.  A write into a clock-gated module is buffered by the
  interconnect, a read gets a slave error.  The "bootloader leaves the
  wdt clock running" assumption came from the 4.14 `arm_wdt` module,
  which was loaded from Android with every clock up - never valid for
  early boot.  Gates (ums9230-clk.c; AON APB syscon @0x64000000, SC
  set register = reg+0x1000):
  `apcpu-wdg-eb` reg 0x08 BIT(30), `ac-wdg-rtc-eb` reg 0x18 BIT(8).
- This also explains why NO 7.1 test ever self-recovered: the 150 s
  software deadline path calls `hawaii_wdt_arm(3)` inside the heartbeat
  timer -> the same abort -> panic-inside-panic -> dead until the
  manual BROM drill.

Test 29 fix set (built, sha 1c5a9981..., packed as boot_71_test29.img
sha 38871d82...):
1. `hawaii_wdt_clk_on()` enables both gates (SC-set writes) before any
   WDT access;
2. the heartbeat feed re-asserts the gate bits every tick
   (`CONFIG_SPRD_UMS9230_CLK=y` is built-in, `clk_disable_unused()`
   would otherwise clear gates without consumers);
3. panic safety net: `hawaii_panic_reset_nb` on the panic notifier list
   leaves the panic text on the panel `hawaii.panicdelay` s (default
   12, photo/OCR window) and then fires the raw ADI -> SC2730 PMIC
   reset - every panic self-recovers from m15 onward;
4. the dim 2x8 status-grid outline is dropped from the banner (user
   request); the single heartbeat slot stays.

## 12. Test 29 RESULT: the WDT gate fix works - and two new mysteries

Test 29 (WDT clock gates + panic safety net + grid outline removed)
booted past the t28 panic point: NO Asynchronous SError panic - the
first statement of kernel_init_freeable() now succeeds, i.e. the two
aonapb_gate clock writes (0x64001008 BIT30, 0x64001018 BIT8) FIXED the
abort.  But:

- **no kernel text on the panel at all** - banner + black text area
  (diag_txt_init ran => end of setup_arch reached, console registered),
  but not a single line appeared, for the whole life of the boot.
- the phone **went down** (power-off-looking) instead of warm-resetting
  - power press did not recover it; a manual BROM drill was needed.
- sysdumpdb: no H71LOG01 => the boot never reached /init (logsave never
  ran); H71RING1 unchanged (the 7.1's pstore console never initializes
  before the death, as established).

Analysis of the no-text symptom: the 7.1 printk (post-6.x rework)
defers legacy console output to the printer kthread that only starts at
`printk_set_kthreads_ready` - an early_initcall (i.e. inside the
initcall window where the boot dies).  vprintk_emit()'s legacy_direct
path evidently did not fire for our console either (t28's replay was
also empty: the photo held ONLY the live panic dump).  The panic dump
printed because panic() forces a synchronous flush.

Test 30 (Image sha 842d0222..., boot_71_test30.img sha e574d5fe...):
three independent observation channels -
1. `console_lock(); console_unlock();` right after register_console()
   (uncontended pre-scheduler, same as console_init's own use) - the
   whole CON_PRINTBUFFER backlog paints at m5;
2. every heartbeat tick: `console_trylock(); console_unlock();` from
   the timer - flushes anything deferred, 1 s granularity;
3. `diag_txt_hb()`: "T+NNNs" painted straight over text row 0 with
   diag_txt_glyph (no printk involved) - a kernel-liveness clock that
   is visible even with zero console output; it also measures whether
   the 150 s deadline reset (hawaii_wdt_arm(3) + raw PMIC reset) is
   what took t29 down, and the timer now arms unconditionally
   (deadline 0 when hawaii.selfreset=0 - observe-only mode possible).

## 13. Test 30 RESULT: 24 dashes, a 15 s power-off - and the no-text root cause

Test 30 (backlog nudge + timer flush + T+ overlay) painted **24 dashes**
= milestones m0..m23 = through the "late" initcall level - by far the
furthest boot yet; the death is entering the DEVICE initcall level
(first real driver probes).  No text, no T+ overlay; the phone powered
off at ~15 s (boot logo 0:19 -> dead 0:34) and needed the BROM drill
again.

Two root causes identified afterwards:

1. **The no-text mystery, solved**: `console_is_usable()` refuses every
   console while `!cpu_online(raw_smp_processor_id())` unless it has
   CON_ANYTIME.  Our console registers at the END of setup_arch -
   before the boot CPU is marked online - so the nudge, the timer
   flush, and every printk flush silently found "no usable console"
   and printed nothing.  t28's panic printed only because CPU0 was
   online by then and panic forces its own flush.
   (Remaining question for t31: why text still failed AFTER the CPU
   came online during the initcalls - the status overlay will show
   the live printk internals on the panel.)
2. **The power-off**: the t29 panic net's raw ADI -> PMIC reset is the
   prime suspect (timing fits: fatal device-level abort -> panic ->
   12 s net delay -> raw reset -> phone goes DOWN instead of warm
   reset).  Note the 4.14 `qogirl6_data` has NO sprd-adi restart
   handler at all (`pmic_wdt_support = false`) - the SC2730 register
   sequence was never proven for this SoC's PMIC.

Test 31 (Image sha 98179903..., boot_71_test31.img sha 002232f6...):
- CON_ANYTIME on the diag console (pure memory writes, safe anytime);
- **the kmsg painter**: `kmsg_dump_get_line()` with a private iterator
  paints records straight from the printk ring at every
  `diag_milestone()` and heartbeat tick - no console list, no
  flush-type logic, no printer kthreads: nothing can silence it; the
  whole backlog paints at the end of setup_arch;
- status overlay: the heartbeat paints "T+NNs c/l/k" (cpu_online,
  have_legacy_console, printk_kthreads_ready) directly over text
  row 1, so the panel SHOWS the printk internals live;
- the panic-net raw PMIC reset is REMOVED (registration deleted): a
  panic now hangs with the text visible (photograph at leisure), and
  the armed 180 s AON watchdog closes the loop with a hardware reset.

## 14. Test 31 RESULT: the panel log works; the killer is clk_disable_unused

Test 31 delivered the first complete on-panel kernel log (kmsg painter +
CON_ANYTIME both contributed), and the panic stayed visible (the raw
PMIC reset removal worked - no power-off, no BROM drill; the armed AON
watchdog closes the loop with a hardware reset ~180 s after the last
feed).  Trace + photo: docs/evidence/2026-11-05-7.1-test31-panic.*

    sprd_gate_is_enabled+0x51/0xa8
    clk_core_is_enabled+0x7c/0xf0
    clk_disable_unused_subtree (x5)
    clk_disable_unused+0xbc/0x1f0
    do_one_initcall -> do_initcalls -> do_basic_setup
    Kernel panic - not syncing: Asynchronous SError Interrupt

`clk_disable_unused` (a late_initcall_sync - the LAST thing
do_initcalls does) walks the clock tree and calls
`sprd_gate_is_enabled`, a plain regmap_read of a gate register.  One
of those gate registers lives in a bus domain still POWERED DOWN in
this bring-up - the read aborts, exactly like the t28 WDT read (write
buffered by the bridge, read = slave error -> sync external abort +
nested SError).  The vendor 4.14 survives the same call only because
its full driver set powers every domain first; which 7.1 domain is
still dead is unidentified (a future task once the boot completes -
candidate: the aon/apcpu power-domain or a regulator driver).

Fix (test 32): `clk_disable_unused()` returns 0 immediately
(drivers/clk/clk.c, commented) - gating unused clocks is a power
optimization only.  Expected: do_initcalls completes, kernel_init
execs the logsave /init, the FULL boot log lands on sysdumpdb
(H71LOG01), and the phone reboots itself back to Android.

Also proven in t31: the panic net's raw PMIC reset was indeed the
power-off culprit path (removed), and the boot reached 1.936 s - the
timestamps are real, so printk time works.  One correction from the
t31 harness verdict: the armed AON watchdog did NOT reset the phone
(the panic sat on screen for the whole 901 s watch window until the
manual power-hold) - consistent with the 4.14 arm_wdt finding that
this SoC's AON WDT counts but its reset output never resets the SoC.
Practical consequence: a panic hangs forever - photograph at leisure,
then power-hold (slot fallback -> rescue -> Android, no BROM needed).

## 15. Test 32 RESULT: the 7.1 boots to USERSPACE

With `clk_disable_unused` skipped, the 7.1 kernel booted completely:
every initcall level, all driver probes, and the logsave ramfs ran as
PID 1 at 1.95 s (photos + trace:
`docs/evidence/2026-11-05-7.1-test32-userspace.txt`).  The LK
environment even confirms our framebuffer guess:
`lcd_base=0x9e000000`.

Two follow-up bugs, both fixed in test 33:

1. `H71-INIT: sysdumpdb not found` after the 8 s wait - the UFS/SCSI
   block device did not appear in time (or did not probe).  Wait
   extended to 30 s; the next panel log shows whether UFS probes at
   all.
2. The logsave `reboot()` ran the fork's
   `sprd_adi_restart_sharkl5` (the SC2730 PMIC sequence bound to
   "sprd,qogirl6-adi") and the phone **powered off**.  The vendor
   4.14 binds NO restart handler for qogirl6
   (`pmic_wdt_support=false`); the sequence was never valid here.
   Removed from the fork - PSCI SYSTEM_RESET takes over (it works
   from a normal boot, unlike the kexec-era finding).

## 16. Test 33 RESULT: PSCI reset also fails; logsave now parks

Test 33 (ADI restart handler removed, logsave waits 30 s) booted to
/init again (logsave up at 1.95 s, "waiting 30 s"), the kmsg painter kept
painting through the wait (12 s deferred probes: hsphy, extcon-gpio,
gpio-keys - USB housekeeping, no UFS lines visible), and then logsave's
`reboot()` powered the phone down AGAIN - so PSCI SYSTEM_RESET is also
unusable on this firmware from the 7.1 (the screen went dark quickly;
the user could not photograph the last lines).

Reset-path summary for the 7.1 on this phone:
- raw ADI SC2730 sequence: POWERS OFF (t32);
- PSCI SYSTEM_RESET (SMC, per the vendor DTB `method = "smc"`): goes
  dark / unusable (t33);
- AON watchdog: counts but never resets the SoC (4.14 arm_wdt finding,

## 17. Test 34 RESULT: UFS never probed - DT binding mismatch, fixed in the DTB

- compatible = "sprd,ums9230-ufs";

- sprd,ufs-anlg-syscon = syscon@64560000 (phandle 0x90),

- vendor reg[0] (0x20200000) is what ufshcd maps; syscons/syscon-names/

## 19. Test 38 RESULT: the reporter bug - and the fix

Test 38's park screen printed `H71-STOR: 0 matching ring lines` while
photo 1 clearly showed `platform extcon-gpio: deferred probe pending`
IN THE RING - so the reporter read nothing.  Cause: **a freshly opened
/dev/kmsg fd starts at the NEXT record** - reading it immediately after
open returns only messages that arrive after the open (none).  Fixed by
`lseek(fd, 0, SEEK_SET)` (rewinds to the oldest record).  Test 39
(boot_71_test39.img sha 2b604ed8...) carries the rewind; the kernel is
unchanged (Image_71_t36).

Also measured in t38: the boot again reaches /init at ~2 s, logsave
waits 30 s, sysdumpdb still not found, park heartbeats run steadily
(0-matches reporter aside, the park machinery is solid), and the ring
contains NO ufs/scsi/blk lines at any point - the UFS driver has still
not produced a single message in any t37/t38 boot (vs t36's -517).
Whether the vcc removal silences a probe that then succeeds, or the
driver's probe is not running at all in these boots, is the question
test 39's rewind-fixed dump will answer: the park screen will either
show the ufs/scsi story or report 0 matches again - and if 0, the
H71-STOR filter will be extended to catch the probe's absence itself
(a "20200000.ufs: no driver" diagnostic against the sysfs view via

Test 40 (boot_71_test40.img sha 36dbe893...): Image 18b3a6ef... (probe

ufshcd_populate_vreg: Unable to find vcc-supply regulator, assuming enabled
OF: /soc/ap-apb/ufs@20200000: could not get #reset-cells for /soc/apapb-gate
ufshcd-sprd 20200000.ufs: failed to get reset ctrl: controller
ufshcd-sprd 20200000.ufs: ufshcd_variant_hba_init failed with err -22

Conclusions:

1. **The vcc-supply fix worked**: the -517 defer is gone; the regulator
   is optional and the driver proceeds.
2. **The new blocker is `devm_reset_control_get()` returning -EINVAL**:
   the fork's reset controller is registered by the apapb-gate CLOCK
   driver (drivers/clk/sprd/ums9230-clk.c binds "sprd,ums9230-apapb-gate"
   and registers a reset controller when the desc has resets), and the
   vendor DTB's apapb-gate node - which the vendor already names with
   the fork's compatible - simply lacks `#reset-cells`, so
   of_reset_control_get() dies before even looking for the controller.
   dtc confirms it on the blob:
   `Missing property '#reset-cells' in node /soc/apapb-gate
   (referred from resets[0] of /soc/ap-apb/ufs@20200000)`.
3. Tooling: the H71-XRAY lines all said "absent" because the initramfs
   never mounted sysfs - fixed (logsave mounts sysfs on /sys).

The fix is one property.  scripts/host/dtb_surgery.py (new tool, this
session) does the surgery without a decompile/recompile round trip:

```
python scripts/host/dtb_surgery.py patch \
    artifacts/testimages/vendor_dtb_t38.bin \
    artifacts/testimages/vendor_dtb_t41.bin \
    --op 'set-prop /soc/apapb-gate #reset-cells u:1'
```

vendor_dtb_t41.bin (sha d3c6e795690ace7f...): identical blob + the one
property; dtc's resets_property warning is gone; fdtget reads back 1;
the UFS node still carries resets = <&apapb_gate 24 30>, the fork clocks
and the anlg/ap-ahb syscons.  The tool keeps every untouched byte (a
decompile/recompile would renumber phandles and re-emit the whole blob),
supports phandle references from paths (p:/path), node/prop ops,
inspection and a selftest.
